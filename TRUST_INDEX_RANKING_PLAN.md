# План внедрения индекса доверия в рейтинг капперов

Проблема: общий индекс доверия каппера уже считается и отображается бейджем, но фактически почти не влияет на позиции. На `/cappers-statistics/` сортировка идет через `ranked_expert_profiles()` по ROI с поправкой на историю, а на `/cappers-table/...` строки сортируются через `_canonical_rank_order()`, который тоже берет этот ROI-based ranking. В таблице `/cappers-table/all/2026-08/` индекс доверия виден на аватаре, но не является явной колонкой и не объясняет позицию.

## 1. Сделать `trust_index` основой общего рейтинга, а ROI оставить вторичным фактором

В `front/expert_ranking.py` изменить `expert_ranking_score(profile)` так, чтобы главным фактором был `profile.trust_index`, а ROI/история использовались как tie-breaker или вспомогательная поправка.

Рекомендованная логика:

```text
ranking_score = trust_index * 1000
              + stabilized_roi_score
              + activity_bonus
```

Важно:

- `trust_index` должен быть главным фактором общего рейтинга;
- ROI не удалить, а использовать после trust index;
- новые капперы с 1 удачным прогнозом не должны обгонять стабильных экспертов;
- при `trust_index = 0` каппер не должен попадать наверх только из-за высокого ROI на малой выборке;
- сортировка должна оставаться детерминированной через username/id.

Обновить сортировку в `ranked_expert_profiles()`:

```python
profiles.sort(
    key=lambda profile: (
        profile.trust_index,
        profile.ranking_score,
        profile.roi_settled_count,
        profile.settled_count,
        profile.followers_count,
        profile.publications_count,
    ),
    reverse=True,
)
```

Если `ranking_score` уже включает `trust_index`, не дублировать его дважды. Главное условие: общий порядок `ranked_expert_profiles()` должен в первую очередь отражать индекс доверия.

Критерий готовности: `/cappers-statistics/` и все места, которые используют `ranked_expert_profiles()`, начинают ранжировать экспертов по trust index, а ROI становится вспомогательным показателем.

## 2. Внедрить trust index в таблицу капперов как видимую колонку и сортировку по умолчанию

В `front/capper_table_service.py` сейчас `_profile_payload()` уже кладет:

```python
"trust_index": profile.trust_index
```

Но таблица `templates/front/cappers_table.html` не имеет отдельной колонки индекса доверия. Нужно добавить колонку рядом с прогнозистом или после него:

```text
Индекс
```

В строке использовать тот же шаблон:

```django
{% capper_trust_badge expert.trust_index %}
```

Сортировка:

- для группы `all` и периода `all-time` сортировать по trust index как основной логике;
- для конкретного месяца, например `/cappers-table/all/2026-08/`, не делать trust index главным фактором, потому что эксперт без активности в месяце не должен быть выше активных участников месяца;
- если выбран конкретный спорт, sport/month metrics должны быть главными, а trust index — вторичным фактором доверия.

Пример ключа сортировки в `build_capper_table_context()`:

```python
rows.sort(
    key=lambda row: (
        row["trust_index"],
        row["roi"],
        row["bets"],
        row["wins"],
        row["followers"],
        row["username"].lower(),
    ),
    reverse=True,
)
```

Если нужно сохранить единый порядок с `/cappers-statistics/`, использовать `_canonical_rank_order()`, но сама `_canonical_rank_order()` после шага 1 уже должна быть trust-based.

Критерий готовности: в таблице есть явная колонка "Индекс"; для `all-time` позиции отражают общий индекс доверия, а для конкретного месяца позиции отражают результаты выбранного месяца с учетом trust index как дополнительного фактора.

## 4. Разделить общий рейтинг и месячный рейтинг

Нужно явно развести два разных режима:

```text
all-time = общий рейтинг доверия
конкретный месяц = рейтинг активности и результата за выбранный месяц
```

Сейчас проблема в том, что при выборе месяца первым может оставаться каппер с самым высоким `trust_index`, даже если он ничего не делал в этом месяце. Это неверно для месячной таблицы: пользователь ожидает увидеть лучших за август 2026, а не лучших вообще.

Правило:

- если `selected_month is None`, то сортировка общая: `trust_index` главный фактор;
- если `selected_month is not None`, то в рейтинг попадают только капперы с активностью за этот месяц;
- для месячного рейтинга главным фактором должны быть метрики месяца: `bets`, `roi`, `flat_profit_percent`, `wins`, `total_profit`;
- `trust_index` для месячного рейтинга использовать как tie-breaker или мягкий коэффициент доверия, но не как первый ключ сортировки.

В `front/capper_table_service.py` сделать отдельные функции сортировки:

```python
def _sort_all_time_rows(rows):
    return sorted(
        rows,
        key=lambda row: (
            row["trust_index"],
            row["roi"],
            row["bets"],
            row["followers"],
            row["username"].lower(),
        ),
        reverse=True,
    )


def _sort_month_rows(rows):
    return sorted(
        rows,
        key=lambda row: (
            row["bets"] > 0,
            row["roi"],
            row["flat_profit_percent"],
            row["wins"],
            row["total_profit"],
            row["trust_index"],
            row["followers"],
            row["username"].lower(),
        ),
        reverse=True,
    )
```

Если нужна более строгая защита от случайных результатов, добавить минимальную активность месяца:

```text
месячный рейтинг: показывать в топе только тех, у кого bets >= 3 или bets >= N из настройки
```

Критерии готовности:

- `/cappers-table/all/all-time/` или общий путь сортируется по trust index;
- `/cappers-table/all/2026-08/` не ставит первым каппера без прогнозов в августе 2026;
- каппер с высоким trust index, но без активности месяца, не попадает в месячные строки или находится ниже активных;
- в месячном режиме trust index влияет только при близких месячных результатах.

## 5. Добавить UI-пояснение и тесты для месячного режима

В UI нужно показать, что выбранный месяц — это не общий индекс доверия, а рейтинг результатов за месяц.

Все время: общий рейтинг строится по индексу доверия.
Месяц: рейтинг строится по результатам выбранного месяца, индекс доверия используется как дополнительный фактор.

В `templates/front/cappers_table.html` рядом с заголовком/периодом добавить короткий текст или tooltip:

{% if period_is_all %}

Добавить тесты:

Критерий готовности: пользователь понимает разницу между "общий надежный каппер" и "лучший каппер выбранного месяца", а сортировка соответствует выбранному периоду.

## 6. Сделать один общий ranking service для всех мест и сортировок

Сейчас разные страницы могут показывать разных "топовых" капперов, потому что порядок формируется в разных местах:

- `/cappers-statistics/` использует `ranked_expert_profiles()`;
- `/cappers-table/...` использует `front/capper_table_service.py` и `_canonical_rank_order()`;
- главная страница и блоки `experts-card` могут брать `ranked_expert_profiles(limit=...)` или другой локальный набор;
- боковые блоки типа "Топовые эксперты месяца" могут иметь отдельную сортировку по подписчикам/ROI/месяцу.

Нужно сделать один источник истины для мест и сортировки.

Создать или расширить сервис, например:

```text
front/expert_ranking.py
```

или отдельный:

```text
front/expert_ranking_service.py
```

В нем должен быть единый публичный API:

```python
def rank_experts(*, period=None, sport_code="all", group="all", limit=None) -> list[dict]:
    ...
```

Где:

- `period=None` или `period="all-time"` означает общий рейтинг по trust index;
- `period="2026-09"` означает месячный рейтинг за сентябрь 2026;
- `sport_code="all"` означает все виды спорта;
- конкретный `sport_code` означает рейтинг за спорт;
- `group` применяет фильтры `all`, `vip`, `paid`, `popular`;
- результат уже содержит `rank`, `profile`, `metrics`, `trust_index`, `ranking_reason`.

Правило: все страницы должны брать порядок из этого сервиса, а не сортировать локально.

Подключить сервис в местах:

```text
front/capper_views.py
front/capper_table_service.py
front/views.py
templates/front/includes/_home_best_experts.html
templates/front/includes/_cappers_pro_cards.html
```

Если где-то нужен только топ-5 или топ-10, передавать `limit`, но не менять формулу сортировки.

Для главной и `experts-card`:

- если блок называется "Топовые эксперты месяца", использовать `period=current_month`;
- если блок называется "Лучшие эксперты", использовать `period="all-time"`;
- подпись блока должна соответствовать периоду, чтобы не было ситуации, где сентябрьская таблица показывает одних, а главная "эксперты месяца" других.

Для таблицы:

- не использовать локальный `rows.sort(...)`, если можно получить `rank` из общего сервиса;
- если таблица должна добавить колонки, она добавляет только отображение, но не меняет порядок;
- `forloop.counter` заменить на `expert.rank`, чтобы место было тем же, что в общем сервисе.

Добавить тесты:

- `/cappers-table/all/2026-09/` и блок "Топовые эксперты месяца" используют одинаковый топ-3;
- `/cappers-statistics/?roi_period=all` и all-time таблица используют одинаковый общий порядок;
- при смене месяца порядок меняется только через общий сервис;
- локальных альтернативных сортировок по ROI/followers не осталось.

Проверка кодом:

```bash
rg -n "ranked_expert_profiles|rows.sort|order_by\\(\"-roi\"|order_by\\('-roi'|followers_count.*sort|_canonical_rank_order" front templates cabinet
```

После внедрения допустимы только:

- сам общий ranking service;
- тесты;
- места, где сортировка не относится к рейтингу капперов.

Критерий готовности: если открыть сентябрьскую таблицу, главную и `experts-card`, одинаковые рейтинговые блоки показывают одних и тех же капперов в одинаковом порядке.
