## ℹ️ 3. Исходное состояние до внедрения

Этот раздел сохраняет причины изменения. Это описание старой реализации,
а не утверждение о текущем коде; актуальные источники приведены в разделе 2.2,
выполненные этапы — в разделе 16.

### ℹ️ Что уже было

- ℹ️ Сервис определяет лидера текущего месяца и лидера за всё время.
- ℹ️ `expert_leader_badges()` возвращает `kind` и `label` для этих двух пользователей.
- ℹ️ Общий include выводит схематичные корону и звезду.
- ℹ️ Include используется, в частности, в hero эксперта, карточках капперов и на главной.
- ℹ️ Есть материальные снимки рейтинга и существующий механизм их пересчёта.
- ℹ️ В публичном профиле есть вкладка достижений и отдельный блок турнирных наград.

### ℹ️ Проблемы исходной реализации

1. ℹ️ Месячный знак означает текущую первую позицию, а не подтверждённую награду за закрытый месяц.
2. ℹ️ Второе и третье месячные места не представлены.
3. ℹ️ All-time представлен только первым местом; нет уровней 2–3 и 4–10.
4. ℹ️ Нет постоянных записей о наградах по месяцам и интервалов лидерства all-time.
5. ℹ️ Одинаковое сравнение ID лидеров выполняется в нескольких местах сборки context.
6. ℹ️ Мобильная карточка публичного эксперта не использует тот же набор знаков, что desktop hero.
7. ℹ️ Не все строки рейтинга и авторские блоки прогнозов подключены к лидерским знакам.
8. ℹ️ `pointer-events: none` у `.expert-leader-badges` мешает поведению «нажать и открыть награду».
9. ℹ️ Общие `fill: none`, `stroke`, круглая подложка и размеры 13 px рассчитаны на старые
   контурные иконки: они исказят многослойные SVG из новых макетов.
10. ℹ️ `rebuild_expert_ranking_snapshot()` удаляет и заново создаёт строки снимка.
    Это актуальная проекция рейтинга, а не неизменяемый архив выдачи наград.
11. ℹ️ `UserAchievement` имеет уникальность `(user, achievement)` — в одной такой записи
    нельзя корректно сохранить победы одного каппера за несколько разных месяцев.
12. ℹ️ `current_month_start()` и месячная статистика используют активный timezone.
    Перед автоматической выдачей нужно исключить зависимость границы месяца от посетителя.

## ✅ 6. Канонический расчёт и факты награждения

### ✅ 6.1. Откуда брать места

Для общего лидерства использовать единственную область рейтинга:

- ✅ месячный: `rank_experts(period='YYYY-MM', sport_code='all', group='all')`;
- ✅ all-time: `rank_experts(period='all-time', sport_code='all', group='all')`;
- ✅ не использовать фильтр VIP, платных, популярных или отдельного спорта;
- ✅ не использовать отображаемый период ROI 30 дней как отдельный общий рейтинг.

Месячный порядок уже задан `_month_entries()`: ROI, flat profit, выигрыши,
прибыль, количество прогнозов и последующие tie-breakers.
All-time уже использует trust-first `ranking_score` и дополнительные факторы.
Эти порядки переиспользуются, а не копируются в сервис наград.

Нужно проверить окончательную детерминированность ничьих. Один и тот же набор данных
должен давать одинаковые места при повторном запуске. Не назначать двух первых мест
и не менять точность сравнения ради визуально одинакового округлённого ROI.

### ✅ 6.2. Граница между снимком и наградой

Снимок отвечает на вопрос «какой рейтинг рассчитан сейчас».
Запись награды отвечает на вопрос «что, кому, за какой период и на каком основании выдано».

- ✅ Снимки можно пересобирать штатным механизмом.
- ✅ Подтверждённая награда хранит копию необходимых фактов независимо от `ExpertRankingEntry`.
- ✅ Не использовать `ExpertRankingEntry` как единственное доказательство после выдачи:
  его строки удаляются при следующей пересборке.
- ✅ `built_at` существующего снимка также меняется; нужна сохранённая дата и версия источника.
- ✅ Награды не создаются при открытии страницы, выполнении template tag или AJAX-фильтрации.
- ✅ Отсутствие snapshot, сбой чтения или ошибка пересчёта не равны отсутствию победителей.

### ➖ 6.3. Исторические месяцы

➖ Восстановление месяцев до октября 2026 исключено из утверждённого запуска.
Ниже — техническое ограничение, а не задача выдать исторические медали.

Текущее построение месячного рейтинга использует не только месячные метрики,
но и актуальные профили/дополнительные факторы. Поэтому пересчёт старого месяца сегодня
не гарантирует точную копию того, что пользователи видели в конце этого месяца.

Для backfill сохраняем происхождение: «восстановлено по доступным данным», дату восстановления
и версию правила. Не называем такой backfill ранее зафиксированным итогом без подтверждения.

## ✅ 7. Доработка бэкенда

### ✅ 7.1. Размещение

Начать в существующем приложении `front`, рядом с рейтингом.
Не создавать отдельное Django-приложение или универсальный движок наград.

Предлагаемое имя небольшого сервиса: `front/expert_awards.py`.
Имена моделей ниже рабочие; закрепить их перед миграцией.

### ✅ 7.2. Период месячной выдачи — `ExpertMonthlyAwardPeriod`

Одна запись на календарный месяц:

- ℹ️ `month`: первое число месяца, уникально;
- ℹ️ состояние: ожидает / готов к выдаче / закрыт / требует разбора;
- ℹ️ `finalized_at`, `ranking_built_at`, `rules_version`;
- ℹ️ число eligible-участников и причина отсутствия победителей, если их нет;
- ℹ️ сохранённое основание финализации и сведения о восстановлении исторических данных.

Отдельная запись периода нужна не «на будущее», а для двух случаев:
блокировка конкурентной финализации и различение «месяц закрыт без победителей»
от «задача не выполнялась или упала».

### ✅ 7.3. Месячная награда — `ExpertMonthlyAward`

- ℹ️ Пользователь-каппер и FK на месячный период.
- ℹ️ Место 1, 2 или 3; металл вычисляется из места.
- ℹ️ Дата выдачи, источник: автоматическая выдача / backfill / административная корректировка.
- ℹ️ Версия правил и сохранённые числовые метрики: ROI, прибыль, дистанция и другие
  факторы, необходимые для объяснения места.
- ℹ️ Состояние: подтверждена / отозвана; причина и автор административной корректировки.
- ℹ️ При корректировке сохраняется прежнее решение, а не только последнее значение поля.

Ограничения:

- ℹ️ не более одной действующей награды на место одного периода;
- ℹ️ не более одной действующей месячной награды пользователю за один период;
- ℹ️ место только из диапазона 1–3;
- ℹ️ подтверждённый период не может быть текущим или будущим незавершённым месяцем;
- ℹ️ награда не зависит от удаляемой строки рейтинга.

Модель хранения исправлений выбрать до миграции: отдельная запись замены/ревизии
либо узкая таблица аудита. Нельзя одновременно требовать неизменяемость и оставлять
обычное свободное редактирование получателя в Django Admin.

### ✅ 7.4. Интервалы all-time — `ExpertAllTimeBadgeTenure`

- ℹ️ Пользователь-каппер.
- ℹ️ Уровень: №1 / Топ-3 / Топ-10.
- ℹ️ Наблюдаемые `started_at`, `ended_at`; открытый интервал означает текущий статус.
- ℹ️ Фактическое место и сохранённые метрики на момент входа в уровень.
- ℹ️ Дата/версия подтверждённого расчёта, по которому открыт или закрыт интервал.
- ℹ️ Данные происхождения: наблюдение с запуска системы или проверенный импорт истории.

Ограничения и поведение:

- ℹ️ один открытый all-time интервал на каппера;
- ℹ️ не более одного текущего №1, двух Топ-3 и семи Топ-10 при полном eligible-рейтинге;
- ℹ️ `ended_at >= started_at`, если интервал закрыт;
- ℹ️ смена места 2 → 3 не создаёт второй серебряный интервал: уровень остался Топ-3;
- ℹ️ смена уровня 1 → 2 закрывает золотой интервал и открывает серебряный;
- ℹ️ повторный одинаковый расчёт не открывает новый интервал;
- ℹ️ после выхода за топ-10 all-time знак исчезает везде публично; закрытые записи остаются только служебным аудитом.

Лимиты общей группы нельзя гарантировать одним `unique(user, ...)`.
Нужны сериализованное применение нового состояния и ограничения БД там, где они применимы.

### ✅ 7.5. Не смешивать с обычными достижениями

- ✅ `Achievement` и `UserAchievement` продолжают хранить обычные достижения.
- ✅ Лидерская полка получает данные из нового реестра и показывается отдельным разделом.
- ✅ Не создавать новую строку справочника `Achievement` на каждый месяц для обхода уникальности.
- ✅ Не включать coins, XP, денежные выплаты или новые push-уведомления автоматически.
- ✅ Счётчики обычных достижений не увеличиваются скрытно от появления лидерских знаков.
- ✅ Турнирные награды сохраняют отдельный источник и существующий показ.

## 🟡 8. Жизненный цикл и фоновые задачи

### 🟡 8.1. Выдача месячных наград

Последовательность:

2. ✅ Проверить согласованный момент финализации и готовность месячной статистики.
3. ✅ Успешно пересобрать канонический месячный рейтинг.
4. ✅ Считать до трёх eligible-победителей из одного подтверждённого результата.

8. ✅ Повторный запуск завершить без дублей и без изменения прежнего решения.

Если eligible-участников один или два, не придумывать недостающих победителей.

1. ✅ Применять после успешного полного пересчёта базового all-time рейтинга.
2. ✅ Получить топ-10 из того же поколения, которое публикуется на сайте.
3. ✅ Сравнить новые уровни с открытыми интервалами.
4. ✅ В одной сериализованной операции закрыть ушедшие уровни и открыть новые.
5. ✅ Не менять ничего для пользователей, уровень которых не изменился.
6. ✅ После commit обновить кэш и отображаемые краткие наборы.

Не запускать выдачу по промежуточному состоянию каждого изменённого купона.
Переиспользовать существующую очередь и debounce пересчёта рейтинга.
Запоздавший worker со старой версией расчёта не должен возвращать старого лидера.

Сбой сборки и технически неполный набор данных не должны массово закрывать интервалы.
Реальный выход каппера из публичного eligible-набора обрабатывается отдельно,

## 🟡 21. Эксплуатация реализованной версии

⬜ Запуск на production ещё не выполнен. Подготовленная последовательность после
выкладки кода (порядок важен: сначала схема, затем процессы):

```bash
docker compose run --rm --build migrate
docker compose up -d --build web celery celery-beat
docker compose exec -T web python manage.py sync_expert_awards --apply
docker compose exec -T web python manage.py sync_expert_awards --check --check-workers
```

Команда с `--apply` пересобирает общий all-time рейтинг, выдаёт текущие уровни,
фиксирует начало наблюдения текущего месяца и догоняет только наблюдаемые периоды.
При первом запуске в октябре первым автоматически закрываемым месяцем будет октябрь,
его закрытие — 1 ноября в 03:00 по `TIME_ZONE`. Celery Beat вызывает
`front.tasks.close_expert_award_months_task` ежедневно в 03:00 для восстановления
после простоя; уже закрытые месяцы не переписываются.

Если код обновлён через bind-mount, уже работающий Celery не перечитывает модули
автоматически. Для запуска новой логики всё равно нужны перезапуск worker/Beat
и синхронизация; одного обновления файлов и применения миграции недостаточно.
После обновления можно проверить регистрацию задачи командой
`docker compose exec -T celery celery -A cappers inspect registered`:
в ответе работающего worker должна присутствовать
`front.tasks.close_expert_award_months_task`.

✅ Read-only preview реализован и выполнялся локально:

```bash

```

статистика пересчитывается из рассчитанных купонов. Поэтому устаревшие месячные
агрегаты могут изменить предварительный список. Данные preview не являются историей выдачи.

и помечается `backfill`, но не входит в утверждённый запуск. Без нового явного
решения пользователя историю не восстанавливаем. Команда не исправляет уже
закрытый период автоматически.

наград после возможного удаления аккаунтов выводится предупреждением.
