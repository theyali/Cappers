# Правила работы над проектом

Главный принцип: код должен становиться проще после изменения, а не “архитектурнее”. Если новая структура не уменьшает дублирование, не улучшает читаемость или не снижает риск ошибок, её не добавлять.

## Работа с репозиторием

- Разработка ведётся прямо в GitHub-репозитории: `https://github.com/theyali/Cappers`.
- Коммиты можно делать прямо в репо, если задача явно завершена и проверки пройдены.
- Перед изменениями сначала читать существующий код и искать текущие паттерны через `rg`.
- Делать минимальный рабочий change-set.
- Не делать unrelated refactor в рамках маленькой задачи.
- Не менять публичное поведение без явного запроса.
- В финале кратко перечислять:
  - какие файлы изменены;
  - что изменено;
  - какие проверки запущены.

## Frontend

### Визуальные правила

- Не добавлять `border` элементам во внешнем виде сайта без явной необходимости.
- Избегать градиентов и overlay.
- Использовать фирменные цвета сайта:
  - `--blue: #0b56fa;`
  - `--ink: #131313;`
  - `--panel: #1f1f21;`
  - `--muted: #707072;`
  - `--yellow: #fbf110;`
- Не добавлять inline styles в templates.
- Не добавлять теги `<style>` в templates.
- Не создавать новые CSS-файлы. В проекте должны использоваться только:
  - `front/static/front/css/main.css`
  - `front/static/front/css/mobile.css`
- Стили для адаптивов держать в `mobile.css`.
- Не добавлять новые `@media` в `main.css`.
- Если уже есть подходящий класс, расширять его, а не плодить почти одинаковые классы.
- Избегать перекрывающих друг друга стилей. Если найдены конфликтующие правила, убрать лишние.

Плохо:

```css
.live { color: red; }
.page .live { color: red; }
```

Лучше:

```css
.live { color: red; }
```

### Шаблоны

- В шаблонах не должно быть бизнес-логики.
- Шаблон получает уже готовый context: labels, urls, flags, counters, statuses.
- Повторяющиеся блоки выносить в общий include.
- Если один и тот же row/card/block используется в нескольких местах, выносить его в include.
- Не обращаться в шаблоне к цепочкам, которые могут вызвать N+1, без заранее подготовленного context.

### Skeleton

В проекте уже есть общий skeleton-сервис:

- `front/static/front/js/skeleton.js`
- `front/static/front/css/skeleton.css`

Skeleton использовать только для крупных async-блоков, где реально возможен layout shift:

- список карточек;
- таблица;
- lazy-loaded блок;
- блок с изображениями;
- область, которая полностью заменяется после fetch.

Правила:

- Для крупного async-блока добавить `data-skeleton-block`.
- Перед fetch вызывать `window.CappersSkeleton?.loading(block)`.
- После вставки данных вызывать `window.CappersSkeleton?.ready(block)`.
- Для изображений использовать wrapper с `data-skeleton-image`.
- У `img` всегда должны быть `width` и `height`.
- Если JS меняет `src` изображения, после смены вызвать `window.CappersSkeleton?.watchImage(wrapper)`.
- Не создавать большие блоки через JS без SSR/placeholder-контейнера финального размера.
- Сначала в шаблоне должен быть контейнер нужного размера, JS только заполняет его.

Skeleton НЕ использовать для:

- обычной отправки формы;
- маленьких AJAX-действий: лайк, избранное, подписка, delete, reaction;
- submit-кнопок;
- inline-status сообщений;
- простого disable/loading состояния кнопки;
- мелких счётчиков;
- dropdown/select/filter controls, если не заменяется большой блок контента.

Для таких случаев использовать обычные состояния: `disabled`, `is-loading`, текстовый status, локальный spinner/icon если уже есть в проекте.

## Backend

### Структура приложений

У каждого приложения могут быть свои:

- `services/`
- `views.py`
- `ajax.py`
- `utils.py`
- `admin.py`
- `globals.py`
- при необходимости `selectors.py` или `queries.py`

Не создавать новые файлы/слои без необходимости. Если задача решается существующим service/utils/helper, использовать его.

Не добавлять абстракции “на будущее”. Абстракция нужна только если уже есть минимум 2-3 реальных места использования или она явно упрощает текущий код.

### Ответственность файлов

- `views.py` — только view-функции: принять request, проверить доступ, разобрать params/forms, вызвать service/utils, собрать context, вернуть `render/redirect/json`.
- `ajax.py` — AJAX endpoints, к которым обращаемся через JS/jQuery.
- `services/` — бизнес-логика, изменения данных, транзакции, внешние интеграции.
- `utils.py` — чистые вспомогательные функции для построения context и форматирования данных.
- `selectors.py` или `queries.py` — сложные queryset/выборки, если приложение становится большим.
- `forms.py` — валидация пользовательского ввода.
- `models.py` — структура данных, простые properties, constraints. Не складывать туда бизнес-сценарии.
- `admin.py` — только настройка админки.

Во `views.py` не держать лишние helper-функции. Если helper нужен для context — вынести в `utils.py`, `services/` или `selectors.py` по смыслу.

В `utils.py` не дублировать функции. Если новая функция похожа на существующую, сделать существующую универсальнее и переиспользовать её.

## Queryset и БД

- Не делать N+1 запросы.
- Для списков использовать `select_related`, `prefetch_related`, `annotate`, `Exists`, `Subquery`.
- Сложные queryset не писать прямо в шаблоне или view.
- Не фильтровать большие queryset в Python, если это можно сделать в БД.
- Не использовать старые поля/флаги напрямую, если уже есть canonical helper/property/service.
- Для списков заранее готовить все данные, которые нужны шаблону.

## Именование

- Имена функций должны описывать действие:
  - `build_*_context`
  - `get_*`
  - `create_*`
  - `sync_*`
  - `annotate_*`
- Не использовать расплывчатые имена:
  - `process_data`
  - `handle_item`
  - `do_stuff`
  - `helper`
- Для boolean использовать:
  - `is_*`
  - `has_*`
  - `can_*`
  - `should_*`

## Изменения кода

- Перед добавлением новой функции сначала найти похожую через `rg`.
- Если найден похожий код, расширить существующий аккуратно, а не дублировать.
- Не удалять старый код, пока не проверены все места использования.
- Не создавать “универсальную архитектуру” ради одной задачи.
- Чем меньше изменение решает задачу, тем лучше.
